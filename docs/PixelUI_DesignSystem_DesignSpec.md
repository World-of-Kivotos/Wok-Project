# 游戏内像素 UI 设计系统（Pixel UI Design System）

> 状态标记：DECIDED = 已拍板（落方向/将落代码）；DRAFT = 本文提议待确认；PENDING = 待实现期/真客户端验证。
> 平台：Forge 1.20.1 / modid `miningdim`，前端经 MCEF 内嵌 Chromium 渲染远端 React 应用。
> 前置真源：

## 一、定位

前置真源定的是"数据地基"，本文定的是"视觉地基"。二者共同构成游戏内 UI 套件的完整规格。

整套游戏内 UI 走 **像素风**，与 Minecraft 本体的像素观感统一。Web 默认审美（圆角、毛玻璃、高斯投影、stroke 矢量图标）是**明确反例**，不是可选项之一。

核心诉求（用户拍板）：**一份 9-slice 资产，拉伸变换出从一个小按钮到一块全屏平板的全部矩形容器控件。** 平板 hub 是最大尺寸端（见 [[unified-ui-entry-plan]]：统一 UI 入口为平板，各功能面板经平板进入），行内小按钮是最小尺寸端，二者共用同一份边框资产且观感必须自洽。

一个环境红利先明确：**渲染目标单一**。UI 只在 MCEF 内嵌的 Chromium 里跑，不面向公网多浏览器，因此**跨浏览器兼容妥协为零**——可以放心使用 Chromium 特性，不需要 polyfill、不需要 Firefox/Safari 回退分支。

## 二、决策定稿（DECIDED）

1. **视觉风格 = 像素风。** `border-radius` 产生的抗锯齿平滑弧线是本规格的头号反例。像素风的圆角必须是阶梯状硬边，由资产位图表达，不由 CSS 几何属性表达。

2. **渲染路线 = 方案 A（真实分辨率布局 + 9-slice 撑尺寸）。** 否决方案 B（低分辨率虚拟画布整体缩放）。取舍依据见第三章。

3. **控件构造法 = 9-slice，用 CSS 原生 `border-image` 实现。** 零第三方库、零 canvas、零 WebGL。四角固定不缩放、四边单轴延展、中心双轴延展——同一份资产撑任意尺寸而边框粗细与角形恒定。

4. **配色 = 灰度资产 + CSS 变量上色，与 9-slice 正交相乘。** 9-slice 解决"任意尺寸"，灰度上色解决"任意配色"。二者相乘：**少量灰度图 × N 个颜色变量 = 整套 UI**。状态（normal/hover/pressed/disabled）与语义（普通/强调/危险）优先靠换色表达，不靠增发资产。

5. **度量 = 全局基准像素单位，所有尺寸取其整数倍。** 半像素是像素风的致命伤，一切非整数倍缩放禁止。

6. **硬红线（禁止项）**，违反即视为破坏设计系统：
   - 禁 `border-radius`（除显式置 0 外不得出现非零值）
   - 禁带 blur 的 `box-shadow`；阴影一律硬色块偏移（如 `box-shadow: 3px 3px 0 #000`）
   - 禁 stroke-based 矢量图标库（lucide 一类）；图标一律像素位图，来源与规格见第八章
   - 禁非整数倍缩放与半像素尺寸
   - 禁抗锯齿字体平滑（点阵字体须配 `-webkit-font-smoothing: none`）
   - 禁位图默认平滑插值（一切放大位图须 `image-rendering: pixelated`）

## 三、方案 A / B 取舍（决策依据）

两条路都能做出像素风，代价分布完全不同。

| 维度 | 方案 A：真实分辨率 + 9-slice | 方案 B：低分辨率虚拟画布整体缩放 |
|---|---|---|
| 布局方式 | 正常 CSS 布局，尺寸约束为基准像素整数倍 | 全 UI 布局在如 384x216 虚拟画布，末端 `transform: scale(N)` |
| 像素完美度 | 高（资产 1:1，需纪律保证尺寸整数） | 最高（天然全局对齐） |
| 中文长文本 | 正常文本渲染，排版自由 | 文字随画布放大，必须点阵字体，长文本排版受限严重 |
| 可变长内容 | 天然支持（聊天、订单列表、商品名） | 需为每处预留固定像素槽位，溢出处理棘手 |
| 事件坐标 | 无需换算 | 需反向换算缩放，与 MCEF 既有 DPI 换算叠加 |
| 响应式 | 照常使用现代 CSS 布局能力 | 基本放弃，只能整体等比缩放 |
| MCEF 缩放风险 | 低 | 高（与 GUI Scale、devicePixelRatio 三重叠加） |

**选 A 的决定性理由**：本项目 UI 的内容形态是数据密集型且中文可变长——跳蚤市场订单簿、商品名称、任务列表、聊天。方案 B 的代价会全部砸在这上面，而它换来的"绝对像素完美"对带大量文本的界面收益很小。

方案 B 不完全废弃：**局部允许**用于内容固定、无长文本的场景（如图标网格、小地图、状态徽章），作为 A 之内的局部技法，不上升为全局架构。

## 四、9-slice 控件构造规格（DECIDED）

### 4.1 原理

```
+---+-------+---+
| 1 |   2   | 3 |     1 3 7 9  四角：永不缩放，任何尺寸下恒为 1:1
+---+-------+---+     2 8      上下边：仅横向延展
| 4 |   5   | 6 |     4 6      左右边：仅纵向延展
+---+-------+---+     5        中心：双轴延展（须 fill 关键字保留）
| 7 |   8   | 9 |
+---+-------+---+
```

直接对整图做 `scale` 是错误做法：边角会被拉成扁形，横竖边框粗细失衡，尺寸差异越大崩得越明显。9-slice 正是为消除该失真而存在，是各主流引擎的标准设施（Unity Sprite Editor 9-slice、Godot NinePatchRect、Unreal Box Brush），CSS 的对应物即 `border-image`。

### 4.2 CSS 实现骨架

```css
.pixel-frame {
  border: 4px solid transparent;   /* 撑开盒模型；border-image 需要边框区域才有地方绘制 */
  border-image-source: url(frame.png);
  border-image-slice: 4 fill;      /* 从图四边各切 4px；fill 保留中心块，缺省会丢弃中心 */
  border-image-repeat: round;      /* 见 4.3 */
  image-rendering: pixelated;
  border-radius: 0;
}
```

三条必须遵守的约束：

1. **`border-image-slice` 的值必须与资产实际边框像素宽精确相等。** 差一像素即整体错位，且错位在小尺寸控件上尤其刺眼。资产与样式的 slice 值必须成对维护。
2. **`fill` 关键字不可省略**，否则中心区域被丢弃，控件变成空心框。
3. **`border-width` 与 slice 的换算关系决定放大倍率。** 若资产 slice 为 4px 而 `border-width` 取 12px，即边角被放大 3 倍——**倍率必须取整数**，非整数倍会破坏像素对齐。

### 4.3 `border-image-repeat` 模式选择

| 模式 | 行为 | 适用 |
|---|---|---|
| `stretch`（默认） | 线性拉伸边与中心 | 仅限纯色或纵向均匀的边；带图案必糊 |
| `repeat` | 平铺 | 可能在末端截断图案 |
| `round` | 平铺并微调使整数次填满 | **带图案边框的默认选择**，像素纹理保持清晰且不截断 |
| `space` | 平铺并均分空隙 | 罕用，空隙破坏像素连续性 |

规则：**边框含任何图案（铆钉、纹路、渐变点阵）一律 `round`；纯色细边可用 `stretch`。**

### 4.4 资产规格（DRAFT）

- 最小尺寸 = `slice*2 + 1`（如 slice=4 则最小 9x9）。实践取 **16x16 或 24x24**，为中心与边留出可辨识图案空间。
- 源图按 **1x 像素密度**制作，放大交给 `image-rendering: pixelated` 与整数 `border-width`，**严禁在美术端预放大出图**（预放大会把插值烘死进资产，后续再缩放必糊）。
- 格式 PNG，索引色或灰度（见第六章），带 alpha。
- 单张资产体积应在 KB 量级——这是像素风对 MCEF 内嵌浏览器加载性能的天然红利。

## 五、度量系统（DECIDED）

设全局基准像素单位 `--px`（CSS 变量），代表一个"逻辑像素格"在屏幕上的实际尺寸。

- **一切尺寸、间距、边框宽、字号均为 `--px` 的整数倍。** 不出现 `1.5rem`、`0.375em` 一类会落在半像素上的值。
- Tailwind 场景下须**改写 spacing scale 与 borderRadius scale**：spacing 全部重定义为 `--px` 整数倍；borderRadius 全档位置 0。默认 scale（`0.25rem` 递增 + `rounded-lg = 0.5rem`）与本规格直接冲突，不可沿用。
- `--px` 的具体取值与是否随 MC GUI Scale 联动，属 PENDING（见第十二章）。

## 六、灰度上色规格（DECIDED 方向，DRAFT 实现）

目的不是"让 UI 变像素风"——9-slice 与度量系统才负责风格。灰度上色解决的是**同一份资产要出 N 种配色**的资产复用问题，两者正交。

### 6.1 单色蒙版（主路径）

资产只提供形状（alpha 通道），颜色完全由 CSS 变量给：

```css
.pixel-icon {
  background-color: var(--accent);
  mask-image: url(icon.png);
  mask-mode: alpha;
  image-rendering: pixelated;
}
```

一张图 + 一个变量 = 无限配色，与主题体系天然咬合。**明确否决 `filter: sepia() hue-rotate()` 那套上色 hack**——不精确、不可预测、无法命中指定色值。

### 6.2 多区上色（后期可选）

单张资产需多个独立染色区时，用通道打包：R/G/B 各存一个区域的 mask，叠三层元素分别 `mask` + 各自 `background-color`。仅在确有需求时启用，不提前上（YAGNI）。

### 6.3 明暗层次

需保留明暗关系（而非纯色剪影）的资产，走灰度存 luminance + 上色层 `mix-blend-mode: multiply` 叠加。注意纯 multiply 下亮部无法超过 tint 色，若需高光须额外叠加一层。此项 DRAFT，待首个带明暗的资产出现时定案。

## 七、资产清单（DRAFT）

"一份资产覆盖全尺寸"在**尺寸维度**成立，但层级与状态维度仍需分别出图。现实规模估计 6-12 张 9-slice：

| 维度 | 条目 |
|---|---|
| 层级 | 外凸窗口框（平板/弹窗）、平面板（分区/卡片）、内凹凹槽（输入框/列表底/进度槽） |
| 状态 | normal / hover / pressed / disabled |
| 语义 | 普通 / 强调 / 危险 |

压缩原则：**层级维度必须出图**（外凸与内凹的明暗关系相反，换色无法表达）；**状态与语义维度优先靠第六章的换色表达**，仅在换色确实无法区分时才追加资产。

对比"每个控件每种尺寸单独出图"的朴素做法，本方案是数十倍的资产量压缩。

## 八、图标规格（DECIDED）

图标一律像素位图，**不引入任何 stroke-based 矢量图标库**。来源按优先级分三层：

| 优先级 | 类别 | 来源 |
|---|---|---|
| 1 | 物品 / 方块图标 | **直接复用 MC 原版贴图**：原版走资产 CDN 的 16x16 贴图，模组物品走服务端 `/v1/item-icon` 端点从 jar 抽 |
| 2 | 功能图标 | **少量自绘 16x16 像素图**：关闭、设置、搜索、确认、取消一类，MC 原版无直接对应物 |
| 3 | 回退 | 像素占位块（保留既有回退链，但**禁止回退到矢量图标**） |

要点：

- **复用 MC 贴图是首选路径**，理由不止省美术：MC 贴图本身就是 16x16 像素资产，与本规格同源，观感天然统一，且随游戏内容自动对齐——新增模组物品无需补画图标。
- 该管线已有可直接沿用的实现范式：回退链 `item -> block -> 模型解析 -> 占位` 配 `image-rendering: pixelated` 放大防糊。**唯一需要改的是回退终点**——既有实验实现回退到矢量图标组件，新实现须改为像素占位块。
- 自绘功能图标统一 **16x16、1x 像素密度**出图，与 9-slice 资产同规格（见 4.4），同样严禁美术端预放大。
- 自绘图标优先做成**单色蒙版**，状态与语义靠第六章的 CSS 变量上色表达，避免每个状态各出一张图。

## 九、字体（DRAFT / PENDING）

中文是本规格最硬的一块骨头：主流中文字体（Noto Sans SC 等）无点阵版本，直接用会与像素资产严重割裂。

- 已知开源候选：**Fusion Pixel（缝合像素字体，8/10/12px 档，覆盖中日韩）**、**Zpix（最像素，12px）**。
- **上述候选的授权条款、字重覆盖、实际渲染效果均未经本项目核实，落地前必须逐项验证，禁止凭印象直接接入。** 标记 PENDING。
- 配套要求：`-webkit-font-smoothing: none` 关闭平滑；字号必须取字体设计档位的整数倍（12px 字体只能用 12/24/36px，用 18px 必糊）。
- 中英混排须用 `unicode-range` 分段，中英文点阵字体的像素基准需对齐，否则基线错位。

## 十一、落地顺序

1. **单点验证（最小成本闭环）**：出 **1 张** 9-slice 边框资产 + 1 个 `PixelFrame` 组件，用同一份资产同时渲染一个行内小按钮与一块全屏平板，直接检验两个极端尺寸下边角与边框的自洽性。此步不碰设计系统全局配置。
2. **度量与主题落地**：确立 `--px` 取值，定义 spacing scale 并将 borderRadius 全档位置 0，接入第六章的 CSS 变量上色。
3. **资产 kit 成套**：按第七章补齐层级 x 状态资产，产出组件层（Frame/Button/Input/Panel/Slot）。
4. **图标与字体接入**：接通第八章第 1 层的 MC 贴图管线，补齐第 2 层自绘功能图标；点阵中文字体接入（依赖第九章验证结论）。
5. **业务视图落地**：按本设计系统实现市场等业务视图。

严格顺序执行，第 1 步未通过则不进入第 2 步——设计系统级建制（度量体系 + 成套资产 + 字体）的成本远高于单个组件，必须先用最小验证证明路线成立。
