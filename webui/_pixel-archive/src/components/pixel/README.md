# 像素原语与灰度上色链路

真源: `docs/PixelUI_DesignSystem_DesignSpec.md` 第四章 (9-slice) / 第六章 (灰度上色) / 第十二章 (PENDING)。
本文只记两件事: **上色方案为什么是现在这个**, 以及**它在 MCEF 里降级成什么样**。

验证页: `#/color-check` (`src/pages/ColorCheckPage.tsx`)。任何改动这条链路的人, 先在真客户端打开它。

---

## 一、要解决的问题

规格第六章的压缩原则是"少量灰度图 x N 个颜色变量 = 整套 UI"。落到 9-slice 上却卡住了:

- `border-image` 把位图原样画上去, CSS 没有任何属性能给它上色;
- `border-image-slice` 的 `fill` 中心块还会盖住元素自己的 `background-color`。

结果是三张灰度资产只能以自身的灰显形, 七个颜色变量一个都影响不到框体。语义档 (强调/成功/危险) 与
亮暗双主题就只剩两条路: 要么每档单独出图 (资产量 x 语义档数, 美术成本按倍增长), 要么框体永远是灰的。

## 二、候选方案与取舍

| 方案 | 结论 | 依据 |
| --- | --- | --- |
| (a) 纯蒙版: `mask-border` / `-webkit-mask-box-image` + `background-color` | 否决 | 见下方"关键实测" |
| (b) 分层合成: 色层 + 混合模式, 灰度图作底 | **采用** | 唯一同时保住"上色"与"斜面明暗"的路径 |
| (c) 多重 background + border-image 混合 | 否决 | 单元素的每个 background layer 都铺满整个盒, 无法裁出 9 个区; 要么拆成 9 个真实子节点, 要么切 9 张图, 两者都把 9-slice 的收口点炸开 |

### 关键实测 (决定 (a) 生死的一条)

用 node 解码三张资产的 PNG (`gray+alpha`, colorType 4), 逐像素统计通道分布:

```
frame-window  24x24  gray: 0x4 16x88 80x42 112x38 160x324 196x38 236x42   alpha: 0x4 255x572
frame-panel   24x24  gray: 0x4 16x88 144x400 184x84                       alpha: 0x4 255x572
frame-inset   24x24  gray: 0x4 16x88 80x42 96x256 104x68 112x38 196x38 236x42  alpha: 0x4 255x572
```

**alpha 通道只有 0 与 255 两个值, 且 0 只出现在四角那 4 个像素上**; 斜面的全部明暗 (外圈描边 16、
暗侧 80/112、中心 96~160、亮侧 196/236) 记在**灰度通道**里。

蒙版 (`mask-border-mode` 的初始值是 `alpha`, `-webkit-mask-box-image` 同样吃 alpha) 只读 alpha,
于是方案 (a) 的产物必然是"一块四角挖空的纯色板": 颜色有了, 斜面全丢。而外凸/平面/内凹三档层级正是靠
斜面方向区分的 (window 与 inset 互为镜像), 层级维度直接作废 —— 这比"框体是灰的"更糟。

`mask-border-mode: luminance` 理论上能取灰度, 但它只能把灰度换算成不透明度, 得到的是"越亮越实"的
单色渐隐, 仍然表达不出"亮侧偏白、暗侧偏黑"的双向关系, 且该值在 Chromium 的支持情况本身未核实。

## 三、采用的方案 (b): 伪元素色层 + overlay 混合

实现在 `src/styles/index.css` 的 `[data-pixel-tone]` 与 `[data-pixel-tone]::after` 两段, 组件侧
`PixelFrame` 只负责下发三个值: `--pixel-frame-src` (资产 URL)、`--pixel-tone` (基色)、`data-pixel-tone` (档位名)。

```
元素自身 background/border  ->  灰度 border-image (照旧, 一行没改)
::after (z-index: -1)       ->  纯色层, mix-blend-mode: overlay, 用资产 alpha 做 mask-border 挖角孔
子节点                       ->  文字与内容, 不参与混合
```

三个设计点各自的理由:

1. **伪元素而不是包一层 div**: 包一层会把 `className` / `ref` / padding 的归属拆到两个节点上,
   调用方与 `PixelCheckPage` 的量测都得跟着改。伪元素不进 DOM, 上层一行不用动。
2. **`z-index: -1` + 父级 `isolation: isolate`**: 前者让色层落在"元素背景与 border-image 之上、
   子节点之下", 于是混合的底色恰好只有那张灰度图, 框内文字不会被一起染色; 后者建立层叠上下文,
   缺了它负 z-index 的色层会掉到父级背景之后, 被不透明的 border-image 完全盖住 —— 表现是"上色毫无效果"。
3. **overlay 而不是 multiply**: multiply 只能压暗, 中心块 (灰度 160) 的最终明度上限被锁死在 63%,
   亮色主题的面板永远是脏灰。overlay 以 0.5 灰为支点双向映射, 恰好复刻原版 MC 面板的结构 ——
   外圈描边压到近黑、亮侧斜面提到近白、中心块落在基色附近。

### 换算公式 (改基色前请按它算)

overlay 以灰度作背景层 `b`、基色作源层 `s` (两者取 0~1):

```
b <= 0.5:  result = 2 * b * s              (向黑压)
b >  0.5:  result = 1 - 2 * (1 - b) * (1 - s)   (向白提)
```

代入三张资产的实际灰度, 得到每个区域的可达范围 (`s` 取 0~1):

| 区域 | 灰度 | 映射 | 可达范围 |
| --- | --- | --- | --- |
| 外圈描边 | 16 | `0.125 * s` | 0 ~ 12.5% (任何基色下都是近黑硬描边) |
| 暗侧斜面 (ring1) | 80 | `0.627 * s` | 0 ~ 62.7% |
| window 中心块 | 160 | `0.745 * s + 0.255` | 25.5% ~ 100% |
| panel 中心块 | 144 | `0.871 * s + 0.129` | 12.9% ~ 100% |
| inset 中心块 | 96 | `0.753 * s` | 0 ~ 75.3% |
| 亮侧斜面 (ring1) | 236 | `0.149 * s + 0.851` | 85.1% ~ 100% (任何基色下都是近白高光) |

两条能直接指导取值的推论:

- **window 的中心块永远比基色亮, 且亮不过 25.5% 以下**。想要更暗的面板只能降资产的中心灰度 (美术侧),
  改基色是徒劳 —— 这是当前占位资产的硬约束, 换真资产后本表须重算。
- 三档 variant 的中心块映射系数不同 (160 / 144 / 96), 所以同一个基色下 window > panel > inset 的
  明度层级是自动成立的, 不需要为层级另配颜色。

`#/color-check` 页第三节把这套公式算出的**预测中心块色**做成实色带贴在框体中心: 无缝即链路与规范一致,
出现接缝就是引擎的实际混合与规范公式不符, 那时基色要按实测重调 (并把这一节改掉)。

## 四、降级表现 (MCEF 的 Chromium 版本仍是 PENDING)

按"降级后什么样"从轻到重排:

1. **两套 `mask-border` 都不被解析** (无前缀的 `mask-border-*` 与前缀的 `-webkit-mask-box-image-*`):
   色层四角不被挖空, 每个角多出 `slice x scale` 见方的一块实色 (当前 `--px:2` / `scale:2` 下是 2x2 CSS 像素),
   阶梯硬边的角略钝。上色本身完全成立。**这是刻意选择的兜底形态** —— 方案 (b) 的主体只依赖
   `mix-blend-mode` 与 `isolation` 这两个 Chromium 41 时代的特性, 把版本风险集中在了这一条可有可无的装饰上。
2. **引擎不认 `mix-blend-mode: overlay`**: `@supports` 整块不生成, 伪元素不存在, 框体退回今天的灰度原样,
   布局/边框/内容零影响。届时全 UI 是灰的但完全可用, 属于"退回批 1 状态"。
3. **引擎认 `mix-blend-mode` 但不真做混合** (未见于任何 Chromium 实现): 色层会盖成一块纯色板, 框体消失。
   这是唯一"看着就废了"的降级, 且无法用 `@supports` 挡住 —— 判据只能是人眼: `#/color-check` 第三节的
   六个框若全是纯色块 (没有斜面), 即命中此档。

对应的检测手段全在 `#/color-check`: 第一节 `CSS.supports` 逐条问引擎、第二节读染色伪元素的 computed style
(`content` 为 `none` 即命中第 2 档降级)、第三节靠肉眼判第 3 档。

## 五、tone 与 variant 的分工 (改之前务必先读)

- **variant 决定形状与明暗方向**, 必须分别出图: 外凸与内凹的高光一个在上/左、一个在下/右, 换色表达不出来。
- **tone 决定这套明暗被染成什么颜色**, 只换 CSS 变量, 不增发资产。

3 张图 x 6 档 tone = 18 种框体。新增语义档只需要在 `index.css` 加一对 `--color-tone-*` (亮暗各一)
并在 `PIXEL_FRAME_TONES` 里登记, 零新增资产、零新增 CSS 规则。

tone **不继承**: 每个框各自决定颜色, 否则一个 danger 弹窗里的所有子面板都会跟着变红。

## 六、已知边界

- `[data-pixel-tone]` 那条规则给了 `position: relative`。需要绝对定位的框请传
  `style={{ position: 'absolute' }}` (行内样式压得过样式表), 而不是用 `absolute` 工具类 ——
  工具类与该规则同为 (0,1,0) 特异度, 而本规则在样式表里靠后, 会赢。`position` 因此刻意没有列进
  `ProtectedFrameStyleKey`, 它是留出来的逃生口。
- 色层是 `background-color`, 不带任何透明度: 半透明色层会让下方灰度直接透出, 与 overlay 的结果叠加成
  不可预测的第三种颜色。基色一律用不透明的 6 位十六进制。
- 本文的灰度数值取自当前的程序化占位资产 (`tools/gen-nineslice.mjs`)。美术真资产接入后, 第三节的
  可达范围表与 `index.css` 里的基色必须一起重算 —— `#/color-check` 的中心块灰度是现场采样的, 会先一步报出偏差。
